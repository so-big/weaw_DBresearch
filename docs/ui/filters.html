Phase 3 · UI brainstorm · step 3 · search filters

DBresearch search filters

On PC the filters sit in a column beside the results and apply as you click. On a phone, the most-used filters are one-tap chips under the search box, and the full list opens in a bottom sheet. Every option shows how many documents it would give, so nobody filters their way into an empty page. Both mocks below work on 12 example documents.

  • ชื่อนักวิจัย (type part of a name)

How it behaves
  • Several ticks in one group mean "any of these". Ticks in different groups must all match.
  • Options that would give 0 results are greyed out.
  • Long groups show 5 options and a "ดูเพิ่ม" link.
  • Clearing the search box keeps the filters.

Two small backend changes this needs

1 · Tick more than one year

The API accepts one value each for fiscal_year, kind and funding_type. To allow "2567 or 2568", they become lists, the way status and category already are.

2 · Counts that don't hide other options

Counts are worked out with every filter applied, including the group's own. So after ticking 2568, the other years drop to 0 and can't be added. Each group's counts should leave out that group's own filter. The mock already behaves this way.

Not in v1

Date-range and budget-range filters. Searching by contract number already works through the search box, e.g. R2568E.
